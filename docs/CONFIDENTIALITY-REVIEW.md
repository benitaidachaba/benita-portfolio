## Case study data contract

Plan a discriminated publication model: `draft`, `needs-approval`, `approved`, `withheld`. Approval records include approved wording/assets, permission scope, evidence reference, reviewer and actual approval date. No dates, signatures or approvers are prefilled. A code flag is a record of permission, not permission by itself.

Keep unpublished narrative and approval evidence in a separate local review source outside route imports. Only an explicitly approved public projection may enter typed public content. Use an allowlist for listings, detail routes, static params, metadata, sitemap and related-project recommendations. Validate that every public project has complete approved fields. Restricted slugs return 404 even when guessed directly. Do not ship draft data and merely hide cards in the browser.

Professional public summaries must include the approved contribution wording, distinguish individual work from team contribution, and describe reporting functionality without exposing internal implementation. Generic workflow illustrations may show conceptual stages only when authorized; do not reconstruct real internal architecture from memory or source.

## Assets and synthetic demonstrations

- Use newly created synthetic names, records and forms, with no mapping to actual persons or proprietary rows. Avoid reusing real identifiers, volumes, dates, geography combinations or document layouts that reveal clients.
- Label illustrations “Synthetic demonstration” and explain their illustrative purpose. Do not portray synthetic figures as verified business outcomes.
- Do not create fake screenshots of delivered products. A conceptual diagram is labeled as such; an actual screenshot requires specific release permission and inspection.
- Check media metadata, filenames, alt text, PDFs, URLs and export layers as well as visible pixels. Redaction requires a flattened, inspected artifact; hiding text with CSS or an overlay is insufficient.
- Keep private approval documents, credentials and original sensitive assets outside Git, `public/`, build output and shared archives. Use a redacted approval reference in project records.

## Release checklist at Checkpoint 4

1. Confirm who may authorize disclosure and obtain permission for exact text/media scope. Record actual evidence without committing sensitive correspondence.
2. Review titles, employer/client references, dates, metrics, tools, diagrams and reporting descriptions against the approved scope.
3. Check source, browser bundles, generated HTML/JSON, social cards, sitemap, PDF exports, images and repository history for restricted information.
4. Verify all reported outcomes and ownership claims. Omit claims lacking evidence.
5. Review all public links; no internal deployment or source-code URLs.
6. Present the concrete public case studies and a redacted review result for approval.

If permission is unavailable, withhold the case study and use verified public independent work. Do not replace it with a fictional client story. If no project evidence is cleared, retain a private preview and resolve homepage scope before deployment.

## Publication boundary

No deployment, public preview link, public source repository or client-media upload is authorized by Checkpoint 1. Local review should use synthetic or supplied general content only. A `noindex` tag does not make a public preview confidential. Re-run the scope review when wording, assets or permission changes.
